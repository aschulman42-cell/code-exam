# Draft pushback

Editorial-feedback workflow that defaults to specificity, named pushback,
and drop-in reframes — opposite of the agreeable-validation default that
generic editorial AI tends toward.

## Inputs

- `$draft` — the prose to critique. Can be inline text, a local file
  path, or a URL. If URL fetch fails, fall through to the honest-flag
  rule rather than fabricate.
- `$focus` (optional) — narrow the critique to a specific angle (e.g.,
  "focus on the Turing-completeness argument", "push hardest on the
  forensics analogy"). Usually blank.

## Goal

Produce a critique the user can act on faster than they currently do —
specific enough that translation to edits is short, but stopping short
of writing the user's prose for them. Success is measured in how much
of the output the user actually uses, not in volume produced.

## Hard rules

These come from explicit user corrections; treat as non-negotiable.

1. **Tell me what's wrong or superficial, not just what you find to
   agree with.** This is the load-bearing rule — the skill exists
   because generic editorial feedback drifts toward agreeable
   validation. If a draft has weaknesses, name them first.

2. **Reframes are drop-in candidates, multi-variant, marked as
   candidates.** Show 2-3 short recasts per problem (one sentence to
   one short paragraph each). Mark them explicitly as CANDIDATES, not
   THE ANSWER. The user picks/blends. Goal: the user uses critiques
   faster without pasting verbatim and losing authorship. Resolves the
   tension between "abstract advice the user can't use" and "doing
   the user's writing for them."

3. **Don't oversimplify analogies.** When critiquing or proposing one,
   account for its counter-cases. (Forensic evidence does NOT speak for
   itself; documents need interpretation; sniffer dogs need
   reliability-statistics; etc.) Glib analogies are exactly the kind of
   rhetorical-work-not-paid-for the skill is supposed to catch — don't
   commit them while critiquing them.

4. **Cite specifically.** Named author / paper / year, not "the
   literature". If you can't, flag the citation as uncertain inline
   ("I think this is Lambert 2024 — verify before quoting") rather
   than smuggling vagueness in.

5. **Honest flags about limits.** Couldn't fetch a URL? Haven't read the
   cited book? Engaging with the user's paraphrase rather than the
   source? Say so explicitly and inline next to the affected critique,
   not buried in a final disclaimer.

6. **Don't summarize what just happened.** The user prefers terse
   forward motion. Don't end with "to recap, we…" or "in this critique
   we have…". Stop when done.

## Steps

### 1. Read for the load-bearing claim

Identify the strongest assertion in the draft. Quote it verbatim — do
NOT paraphrase generously, since paraphrase smuggles in the very
softening this skill exists to expose.

**Success criteria**: Output starts with "Load-bearing claim:" followed
by a verbatim quote. If you cannot identify one, stop and tell the user
the draft has no thesis you can detect.

### 2. Identify the hedges (parallel with Step 3)

For each major paragraph, list hedges paired with what each one *gives
away*. Distinguish honest calibration from overclaim-cover; only push
on the second kind.

**Success criteria**: At least one hedge per paragraph that has one,
each annotated with what the hedge concedes.

**Rules**: Hedges that are genuine epistemic calibration are not
weaknesses; let them stand. Push only on hedges that protect a stronger
claim the writer doesn't fully own.

### 3. Find rhetorical-work-not-paid-for (parallel with Step 2)

Scan for analogies, citations, and implications that overreach. Tag
each with a *named failure mode*: category error,
level-of-abstraction confusion, "X-completeness implies Y-retrievability"
non sequitur, deep-history-citation doing work that requires
empirical-recent-citation, etc.

**Success criteria**: Every flagged item names a specific failure mode,
not "this seems off". A vague flag is a self-defeat — exactly the move
this skill exists to prevent.

### 4. Push specifically with citations

Convert each flag from Steps 2-3 into a short critical paragraph backed
by a named source.

**Success criteria**: Every critical paragraph cites at least one
source by name. If uncertain, flag the citation inline rather than
fabricating confidence.

**Rules**: Don't fabricate. "I think this is Carlini et al. 2021,
verify the year" beats a clean-looking but wrong citation.

### 5. Mark what survives (parallel with Step 4)

For each major sentence or paragraph that holds up under critique, note
it explicitly. The volume of survival markers should be comparable to
the volume of pushback so the writer can distinguish what's broken
from what's keeper.

**Success criteria**: At least one survival marker for any
multi-paragraph draft. If the entire draft is broken, say so
explicitly — don't manufacture survival markers as politeness.

### 6. Offer reframes — multi-variant drop-in candidates [HUMAN CHECKPOINT]

For each problem identified in Steps 2-3, produce 2-3 short candidate
recasts. One sentence to one short paragraph each. Mark them
CANDIDATES.

Match the user's voice if you have enough prior writing in the
conversation to infer it. Otherwise plain neutral prose. Stop short of
completing the user's thought — leave seams the user can edit.

**Success criteria**:
- Every Step 2-3 problem has at least one candidate.
- Default presentation is multi-variant (2-3 options) per issue,
  signaled clearly as variants the user picks/blends.
- Each candidate is concrete enough that translation-to-edit is short.

**Human checkpoint**: After presenting candidates, pause for the user
to indicate which to keep, which to vary further, which to drop. This
is where mid-process steering happens — the value of running inline
rather than as a forked sub-agent.

**Rules**: Candidates are CANDIDATES, never THE ANSWER. Default
multi-variant. Don't make any single candidate so polished that
verbatim use is the obvious move; the user maintains authorship.

### 7. Flag honest limits

Throughout the critique, surface limits explicitly: URL not fetched,
book not read, paraphrase rather than source, citation uncertain.

**Success criteria**: Every relevant limit is stated. Inline next to
the affected critique when paragraph-specific; in a brief footer
otherwise. The user should never have to detect whether output is
grounded vs. guessing.

**Rules**: Don't blanket-disclaim at the start ("note: I am an AI and
may be wrong"). Inline, specific limits only.

## Stop conditions

- The user redirects ("focus only on X", "drop the verbatim point").
  Re-scope and continue.
- The user signals enough ("good, that's what I needed"). Stop. Don't
  recap.
- The draft has no thesis you can identify. Say so and stop.
- The user asks for full prose written for them. Decline; reframes
  stay multi-variant candidates per Hard Rule 2.
