# CodeExam screenshot-quality iteration

## What this is for

Andrew is iterating on CodeExam's GUI output to use in articles on his website. Each article surfaces small imperfections that internal testing wouldn't have caught — wrong renames, false-positive prompts, inflated function boundaries, missing clickables. The fix loop has a recognizable shape, and getting it right matters because every imperfection in a screenshot becomes credibility damage in print.

This skill encodes that loop. It does NOT include CodeExam architecture knowledge (that lives in `CLAUDE.md` / `MEMORY.md` / `CodeExam_overview.md`); it just structures the *flow* of an iteration.

## When to apply

Trigger on any of:
- A screenshot reference (`see CodeExam_*.jpg`, "in the screenshot", "looks wrong in")
- A specific GUI complaint ("duplicate", "(file scope) but should be Y", "not clickable", "hangs the browser")
- An article-context framing ("for the article", "before I publish", "the screenshot shows")
- An "I'd like to fix this" without further detail when CodeExam is the active project

When in doubt, treat the user's mention of a CodeExam visual artifact as an implicit fix request and apply the workflow.

## The workflow

### 1. Identify the specific imperfection

Tell the user explicitly, "I am really using .claude\skills\codeexam-screenshot-fix\SKILL.md".

Don't guess. Ask the user what they see, or read the screenshot carefully. Articulate back the specific defect in concrete terms — "two L906 entries with the same function" beats "duplicates somewhere".

### 2. Diagnose with a minimal repro before touching code

For most CodeExam features, a one-shot `node -e` invocation against the existing index reveals what's happening without a rebuild:

```bash
node -e '
import("./src/core/CodeSearchIndex.js").then(async ({ CodeSearchIndex }) => {
  const idx = new CodeSearchIndex({ indexPath: ".cli_js_3" });
  const { collectPrompts } = await import("./src/commands/prompts.js");
  const prompts = await collectPrompts(idx, { filter: "..." });
  // ... print what you need to see ...
});
'
```

This costs ~2-15 seconds depending on the file (cli.js is ~12s for tree-sitter passes). It avoids the much-slower full index rebuild. When you find a discrepancy between what the user reported and what the code returns, you have a real bug isolated. When the code already returns what was expected, the issue lives in rendering (GUI side).

### 3. Honest scope flag — cosmetic vs. correctness

Before any code change, classify the fix as one of:

- **Correctness**: changes what the tool reports (wrong rename, missed prompt, inflated function bound). Just fix.
- **Code quality**: refactor that improves source DRY-ness or readability without changing what the tool reports. Mention it explicitly: "this is a code-quality cleanup; will not change screenshots."
- **Cosmetic-only with risk**: changes only display, may introduce subtle changes elsewhere. Flag the trade clearly. Andrew has rejected cosmetic-only refactors that touched live LLM prompt text — don't do that without explicit sign-off.

Andrew dislikes refactoring as the goal; refactoring as the means to better screenshots is OK only if it cleanly produces better screenshots.

### 4. Fix in the right layer

Map the imperfection to the right file before editing:

- **Wrong function attribution / inflated boundaries** → `src/core/CodeSearchIndex.js` parser path, or `src/core/TreeSitterParser.js` AST walk
- **False-positive or missed prompt detection** → `src/commands/prompts.js` (Pattern 1-6 detectors)
- **Composite-prompt expansion (ternary, template, array.join)** → `src/commands/prompts.js` `_expandCompositePrompts` and helpers
- **Digest content (callers, callees, strings)** → `src/commands/digest.js` formatter, `src/core/CodeSearchIndex.js` `buildFunctionDigest`
- **Pure GUI rendering issues (clickability, layout, color)** → `public/app.js` / `public/style.css` / `public/index.html`
- **Endpoint / data-shape issues** → `src/server.js` route handler

If the fix touches multiple layers, do the deepest one first (parser → command → server → GUI) so each layer's verification is meaningful.

### 5. Verify with the same repro

After the change, run the exact repro from step 2 again. If the output matches what the screenshot should show, the data layer is fixed. For GUI-only changes, give the user explicit refresh instructions:

- Server changes (`src/server.js`, anything `src/` server-touching): user must Ctrl+C and re-run `node src/server.js …`
- `public/` changes only: hard-refresh in browser (Ctrl+Shift+R)
- Index-format changes: full rebuild (rare; flag explicitly)

### 6. Commit at the size of the change

This is important — commit message length should match change weight, not the time spent debugging.

- 5-line targeted fix: subject + 2-3 sentence body. Done.
- Substantive feature work (new endpoint, new pass, new component): subject + 5-15 line body covering motivation, approach, tradeoffs, what's deliberately NOT done. Worth the prose.
- Refactors purely for screenshot quality: short message; explain what you DIDN'T change as much as what you did.

If the message draft starts feeling padded, it probably is. Trim.

### 7. Don't claim completeness

If a previous session's fix didn't fully solve the issue (e.g., "we still see Xf in the GUI even after the fix"), the most likely explanation is a stale process — old server still running, old index, old browser cache. Walk through the cache-bust list (server restart, index rebuild, hard refresh) before re-investigating the code. The session has hit this pattern repeatedly.

## Things to remember

- Andrew prefers reviewing diffs over taking changes on faith. After a fix, summarize what changed and where, then let him test before assuming success.
- `--prompt-catalog` and digest features are load-bearing for articles. Treat regressions there as high-priority.
- Avoid cli.js-specific tuning — prefer patterns that generalize. Same goes for screenshot fixes.
- The full test suite has 6 pre-existing failures unrelated to current work. Same-baseline pass count is the right regression check, not "0 failures."

## What this skill is NOT for

- Adding new features to CodeExam from scratch (use the design-flag-before-code pattern from memory; that's a different workflow).
- Article writing or editing (Andrew handles his prose).
- General Node.js debugging unrelated to a visible CodeExam artifact.
