Last night I generated /vocab and /struct-dupes-all listings from several large indexes. Some observations:

.python310pyop -- this large index (inverted index is 755 MB) includes both *.py from all the Python packages I have installed here, plus .op files generated from *.pyd and *.dll files that provide the non-Python (C/C++?) basis in binary form. 
In /struct-diff-all, right now looking at a lot of truncated names like "AdmissionregistrationV1alpha1A" and "AppsV1Api.patch_namespaced_con". Fix not yet implemented to stop truncating names in output from commands like this? 
/vocab output could also use extra line between each row. After some generic stuff at top like ValueError, __name__, __all__, we fairly quickly get to some useful vocabulary: lambda, torch, numpy, Tensor, num_attention_heads, num_hidden_layers, max_position_embeddings, openai_types, attention_mask, ... Would be good if there were a higher concentration of those, and less of version, device, testing, array, copy, etc. So your CamelCase/snake_case bonus, in addition to perhaps a little more oomph for lengthy identifiers, would help.

.android-java -- medium size index (190 MB literal index) includes *.java decompiled from Android binaries. 
/struct-diff-all output is clean and readable. Top is: getIntent, attrcreatedocumentfragment, attreffectivevalue, onCreateDescription...
/vocab needs the blank lines. Top is IllegalArgumentException, DOMTestDocumentBuilderFactory, DOMTestIncompatibleException, TestTargetClass. Some of the scores may be distorted because when decompilation fails, you instead get lengthy disassemblies into JVM bytecodes, so functions appear to be much longer than they would be if expressed in Java.

.progfiles -- similar to .win11op, but generated from \progra~1 and \progra~2 (64-bit and 32-bit Program Files), inverted index 2.9 GB, literal index 2 GB. 
/struct-dupes-all output has lots of truncated names like "Microsoft_EdgeCore_144_0_3719_", "Microsoft_Office_root_Integrat", "Microsoft_Visual_Studio_18_Bui". All come from *.op files, of course. Given each .op file is a single pseudo-function with a bunch of strings inside it, what does "same code structure, different names/values" mean here? Probably that entire files are identical or nearly so. Is there a chance that the function-level dupes here are just picking up on SHA1-identical files?
/vocab is interesting. Top includes: CompilerServices, PublicKeyToken, QueryPerformanceCounter, GetSystemTimeAsFileTime, IsProcessorFeaturePresent, GetCurrentProcessID, AcquireSRWLockExclusive, IsDebuggerPresent ... Most of these sound like Windows API calls or NT API calls. To be expected, but not quite vocabulary specific to things in Program Files like Excel and MS Word. I should try /vocab excel if that's a valid command. It is, but it just shows the vocabulary word "Excel", not vocabulary that comes from paths/files that refer to Excel. Easy enough to do /vocab 4000 > progfiles_vocab.txt, then ! findstr Excel progfiles_vocab.txt, which will just get the cases where /vocab happened to include an Excel .op file among the "representative files". I guess I was hoping to see some Excel-specific vocab like recalc or trendline or regression, but instead more generic stuff, though a bunch of it is re: StateMachine, which may or may not be telling us something interesting. 

So far, I'm feeling /vocab needs to somehow be tied more to the domain-specific vocabulary, which domain may be the entire index ("how is this codebase different from all other codebases?"), or the domain represented by top-level folders within the codebase, or within a specific file, or group of files (that group defined by the shared vocabulary that is not shared by other files within the same codebase).  

.spinellis -- Medium-size index (437 MB literal, 287 MB inverted) created from the open-source on CD that came with the book "Code Reading" by Spinellis. I guess I was hoping (without really expecting) that the tool would be able to sort-of "partition" the collection back into the top-level directories representing what's on the CD like NetBSD, Apache, etc., but where the partitions/groups would be surfaced from low-level details like vocabulary. Very vague thinking, but perhaps you can see what I'm getting at.
