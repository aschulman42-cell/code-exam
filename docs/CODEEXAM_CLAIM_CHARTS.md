## 1. What a CodeExam claim chart is, and is not

A CodeExam claim chart records, for each element of a patent claim and each code target, whether
the model found code that plausibly meets one reading of that element, with the lines it relied
on. A `PRESENT` cell is a **candidate match for a stated reading**, a lead to verify by reading
the cited lines. It is not a finding that the limitation is met, and it says nothing about
validity or infringement. When a CodeExam chart is compared with a chart a party filed in court,
a match is **agreement with that party**: plaintiff and defendant chart the same claim against
the same code and reach different results, and both can be internally sound, because they encode
different contentions. CodeExam is a tool for building and pressure-testing contentions and for
surfacing *candidates*, not an oracle that settles them. The verdict labels and the methodology are
in [`CODEEXAM_PATENT_CLAIMS.md`](CODEEXAM_PATENT_CLAIMS.md); read its first section before
anything here. No page before this one listed every claim-related command; section 2 does.

**Why "CodeExam claim chart" rather than "claim chart".** A chart a party files is advocacy
prepared by counsel, often with input from an expert: it rests on a claim construction the party
will argue, cites evidence the party will stand behind, and is signed. A CodeExam claim chart is
a working draft produced by a program. Its rows are CodeExam's deterministic split of the claim,
or the practitioner's own rows through `--elements`; its candidate code is what retrieval or the
examiner supplied; its verdicts and citations are a model's, checked against the index for
existence but not for meaning. It is the starting point for the examiner's own chart, to be read
with the cited lines open, and nothing in it should be dropped-in as-is into a contention,
declaration or expert report, however good the charts become, in CodeExam or in the planned
[CodeClaim](CODEEXAM_CODECLAIM.md). A code examiner must *verify* code references (and strive
to verify assertions that a claim element is *absent* in the code). The parts an AI model fills
can be wrong in ways a deterministic table cannot: a verdict argued from the wrong lines, a
citation that exists but does not say what the cell claims. Which parts are deterministic and
which are the model's is stated in [`CODEEXAM_PATENT_CLAIMS.md`](CODEEXAM_PATENT_CLAIMS.md)
under "Determinism around the model" and in
[`AI_ASSISTED_CODE_EXAM.md`](AI_ASSISTED_CODE_EXAM.md).

## 2. What it can do today

**The commands, in one place.** Every claim-related flag, by the direction it works in. Each
runs on a cloud engine or a local GGUF model alike, and `--air-gapped` enforces no cloud; any of
them can be run on an open-source codebase today, which is where the examples below come from.
Reference entries are in [`cli.md`](cli.md) and `--help`; the concepts in
[`CODEEXAM_PATENT_CLAIMS.md`](CODEEXAM_PATENT_CLAIMS.md) and
[`CODEEXAM_PSEUDO_CLAIMS.md`](CODEEXAM_PSEUDO_CLAIMS.md); the working notes in
[`claims-pipeline-state.md`](claims-pipeline-state.md).

The flow, in three steps:

```text
[1. Split]                      [2. Retrieve and verify]           [3. Chart]
claim text -> element rows  ->  names searched, verified,      ->  per element and target:
(the splitter, or --elements)   navigated: --claim-locate          PRESENT / PARTIAL / ASSUMED /
                                writes a targets file               ABSENT with cited lines:
                                                                    --claim-chart --targets
```

Deterministic code owns steps 1 and 3's table; a model supplies step 2's code words and
choices and step 3's cell verdicts. The whole-claim search (`--claim-search`, multisect) is an
alternative step 2 over file bodies; pseudo-claims run the arrow backwards.

**Retrieval and target discovery** (claim to code, per element):

- `--claim-locate <claim>` splits the claim into elements, asks the model for the code words each
  element would wear, searches the index's symbol names for them, verifies every name against the
  index, navigates callers and callees (promoting callees up to two hops down since 2026-10-22,
  bounded), and has the model choose implementers; it writes a targets file with provenance
  through `--targets-out`.
- `--blind` hides file paths and the codebase's identity from the model, so a hit is discovery
  rather than recall. `--runs <n>` repeats the cycle and keeps what any run proposed, tallied.
  `--per-element-select` chooses implementers with one model call per element instead of one
  pooled call (measured: fewer, denser targets, worse recall on the crux symbol).
- `--hunt` lets the model drive its own search of the symbol table, capped by `--hunt-rounds` and
  `--hunt-calls`; `--no-hunt` forces it off. `--propose-from-priors` is the legacy path, names
  from the model's own knowledge, useless on confidential code. `--include-tests` admits test,
  mock, benchmark and example symbols as candidates (held back by directory, file name or
  symbol name since 2026-10-22); `--no-navigate` skips the hop (absent from `--help`).
**Chart generation:**

- `--claim-chart <claim>` returns, per target and element, `PRESENT`, `PARTIAL`, `ASSUMED` or
  `ABSENT` with line citations, a coverage line per element and a provenance header naming the
  engine, the build and the targets checksum. Targets come from `--targets` (a list, or the file
  `--claim-locate` wrote) or, with none given, from per-element retrieval.
- Per-element retrieval is sized by four flags: `--targets-per-element` (candidates analysed
  per element, default 3), `--max-retrieved-targets` (the cost ceiling on the total, default
  30), `--whole-claim-targets` (targets from the claim's own words, default 5) and
  `--concentration-targets` (a file several elements point at, default 3).
- `--elements @file` supplies the rows, one limitation per line, in place of the heuristic split.
  `--claim-family` charts claim 1 and every dependent beneath it; `--claim-number` picks a claim
  from a numbered file; `--dep-synonyms` lets a narrowing dependent donate vocabulary to the
  parent row it narrows (off by default, measured to dilute). `--no-callees` omits callee bodies;
  `--scope-note` states a structural fact once; `--include-op` admits binary string dumps.
**Output and formatting:**

- `--verdicts-out` writes the per-target verdicts as JSON, the merge's input and the sidecar every
  replay reads. `--chart-html` writes a self-contained printable page, `--chart-format brief` the
  traditional two-column layout, `--chart-html-from <sidecar>` re-renders without a model, and
  `--chart-notes`, `--chart-title` and `--chart-subtitle` dress it.

**Whole-claim search** (claim to code, one search for the entire claim):

- `--claim-search <claim>` extracts the claim's distinctive terms and runs them as a multisect
  search over file bodies, gated by `--min-terms`; `--claim-file` reads the claim from a file.
- `--claim-analyze <claim>` is the end-to-end form: extract, search, analyze the top matches;
  given a function and `--claim-text` it element-maps the claim against that one function.

**Pseudo-claims and the self-test** (code to claim):

- `--pseudo-claims <anchors>` drafts claim-shaped descriptions of what code does, one claim per
  anchor group, with the anchors attached; `--claims-only` writes the machine-readable claims and
  their anchors sidecar; `--claim-class` sets the statutory class; `--claim-schema` (experimental)
  has the drafter fill a claim object whose frame is the litigated population's;
  `--pseudo-claims-chart` renders each draft as a chart; `--doc-anchors` adds documentation
  anchors; `--triage` ranks a run's drafts deterministically; `--pseudo-out` and
  `--include-evidence-pack` shape the artifact. `--candidates <file>` discovers the anchor groups
  to draft from, deterministically, with `--filter` and `--group-by` to narrow and `--rank` to
  order them by a model's priority; `--ground-truth` scores a candidates run against a
  hand-authored anchors list; `--shape-profile` names the population a draft should resemble
  (litigated, the default; ai-ml, 841 AI/ML claim 1s; randpat, 5,395 all-art independents).
- `--synonymize <claim>` rewrites a claim's wording away from the vocabulary a programmer would
  use, one model call per limitation, so a corpus with known answers becomes a test of retrieval
  (`--synonymize-out`, `--claims-per-line`, `--single-claim`).
- `--claims-loop <chart>` fills a pseudo-claim chart's empty cells and measures draft-to-retrieve
  agreement, flagging claims that need a redraft.

**Engines.** `--llm` picks a cloud provider and `--model` a GGUF; `--local-reasoning off` is
required for a thinking model such as Gemma 4; `--reproducible` pins a run
([`REPRODUCIBILITY.md`](REPRODUCIBILITY.md)).

**In the GUI and in Chat.** The GUI carries Claim Search and Claim Analyze (with an LLM
claim-search variant and a claim-text box) and nothing else of the family: `--claim-locate`,
`--claim-chart`, `--pseudo-claims` and `--synonymize` have no GUI surface (#343). In Chat and
other MCP clients the `claim_elements` and `claim_candidates` tools expose the splitter and the
deterministic half of `--claim-locate`'s retrieval; the audited chart stays on the command line
([`CODEEXAM_MCP.md`](CODEEXAM_MCP.md)).

**Two retrieval mechanisms, each with a blind spot** (from the pipeline notes, 2026-08):

| | whole-claim (`multisect`, `--claim-search`) | per-element (`--claim-locate`, `--claim-chart`) |
|---|---|---|
| unit | one search for the entire claim | one search per limitation |
| the model emits | regex search terms | code words per element |
| searched against | file body text | symbol names only |
| gate | quorum (`--min-terms`) | none; ranked, 25 per element,<br>then up to 35 more by name at the cap (2026-10-22) |
| blind spot | well-named single-purpose functions | badly-named functions;<br>names carrying none of the claim's words |

- **A real patent against a real codebase, no hand-supplied targets.** `--claim-locate` on the
  '101 patent's claim 1 against ExoPlayer 3 (Claude, pooled selection, n=1, 2026-08-13): ten
  elements, 28 symbols located, among them `AdaptiveTrackSelection::determineIdealSelectedIndex`,

  model named. Claude's element words translated the claim rather than echoing it (`bitrate`,
  `codec`, `buffered`, `playback`, `decode`, `adapt`, `deadline`).
- **Coverage and variance on a small corpus.** On `.demo`, a contrived TLS corpus, `--claim-locate`
  found 5 of 5 element groups against the README's answer key (Claude, pooled, n=1, 2026-08-12);
  over five runs pooled selection lost nothing and per-element selection lost element (e) in 2

  exceptions. `.demo` flatters the tool: Claude wrote the code and the claims around each other,
  and no `.demo` result transfers to a real patent without re-measurement.
- **A negative control.** A claim paired with a codebase it cannot read on; the first such chart
  scored 4 of 4 `ABSENT` (n=1). An engine that does worse than the constant answer is worse than

- **Real-world filings, 2026-10-21** (Claude Sonnet 4.6 through CodeExam, n=1 per row; section

## 3. Real-world grounding

**Two patent populations.** The claims pipeline is calibrated on a corpus of about 385 software
patents that have been asserted in litigation, claim 1 with its dependent chain, drawn from the
USPTO Patent Litigation Docket Reports data (March 2024 release; cases to about 2020), with the
claim structure cross-checked against Google Patents and the USPTO weekly grant XML: on the order
of 85,249 markup-verified dependents, with about 554,000 canonical claim-1s as the wider
backdrop. A second population, from the USPTO's Artificial Intelligence Patent Dataset, covers
the subject matter CodeExam's AI/ML detectors target. These are the populations the tool is
built for and tuned on; no single example is a yardstick (a rule the work keeps: calibrate on a
population, never on the case in hand). The litigated corpus's claim-1 texts are in the
repository as
[`test/fixtures/litigated-claim1-structure.jsonl`](../test/fixtures/litigated-claim1-structure.jsonl)
(380 records, 840 KB: patent, original assignee, grant date, claim text); the full fetch with
each claim's dependent chain is written outside the repository by
`scripts/litigated-claims-fetch.mjs`. The AI-patent population's claim texts are not in the
repository; what it derives from them is: the frame counts for 841 AI/ML claim 1s of 2013 to 2017
in `src/core/claim-frame-tables.json`, the shape bands `--shape-profile ai-ml` draws on in
`src/commands/pseudo-claims.js`, and the vocabulary profile in `src/core/claim-genre-df.json`.

**The measured shape of a litigated claim 1** (frame tables, deterministic, 2026-10-19). 380 of
the 385 families yield a parseable claim-1 structure; each count below excludes the rows where
its feature is absent and names its own denominator. Of 380 structure rows: method 187, system
70, computer-readable medium 15, Jepson 35, other 73. The transition is `comprising` in 97.6% of
378 (`the steps of` tail in 21%). Of 956 method-claim rows beyond the preamble, 80.8% open with
a gerund (`receiving`, `determining`, `providing`, `generating`). Of the 3,257 dependents that
carry a reference phrase (36 do not), 72.8% use `of claim`; of the 3,210 that carry an opener (83
do not), 76.6% open with `wherein` and 17.2% with `further comprising`. These tables,
`src/core/claim-frame-tables.json`, are what `--claim-schema` enforces on a drafted pseudo-claim's
frame through `src/core/claim-schema.js`, which renders the claim object the drafter fills.

**Three tiers of test**, by what kind of answer exists:

- **Structural, no model.** Does CodeExam's own element-splitter and dependency-detector
  reproduce the patent office's markup? The dependency detector disagrees with the PTO's
  parent on none of the 3,293 dependents of claim 1, with 4 unresolved
  (`claim-frame-tables.json`, `parentAgreement`); the element-splitter agrees less often and is
  being calibrated.
- **Negative controls.** Truth is `ABSENT` by construction; any `PRESENT` is a false finding.
  First chart 4 of 4 `ABSENT`.
- **Positive screening.** Retrieval only: where a patent's assignee also publishes open source,
  multisect ranks indexes by how many of a claim's distinctive terms co-occur. This measures
  retrieval, not infringement.

**The self-test, "huffing our own fumes" (HOF).** Every claim-to-code answer key in hand is
compromised: a hand-built set is tiny, `.demo` was written by a model together with its own
claims, and a real patent shares vocabulary with its own implementation, so a match can be word
overlap rather than skill. HOF manufactures an answer key on any index in three steps: draft
pseudo-claims from code with the anchors they were drafted from attached (`--pseudo-claims
--claims-only`); have a *different* model reword them away from the code's vocabulary with the
anchors withheld (`--synonymize`, the load-bearing step, since it creates the gap between claim
words and identifiers that `.demo` lacks and a real patent has); feed the reworded claims back
through `--claim-*` and score whether the same anchors resurface, assigned to reasonable
limitations. The name is the caution: CodeExam wrote the claim and then went looking, so the loop
confirms a floor of capability, not claim-to-code skill against an outside key. Its lesson
(2026-08-19, two corpora, `scripts/anchor-recall.mjs`): the single number is the wrong number.
Scored on the granularity ladder, "100% reached" was overwhelmingly the right class or the right
file; function-level recall was 5 to 8%, and for a chart a class is not a citation, because the
limitation is implemented by the method. The write-ups are
[`CODEEXAM_PSEUDO_CLAIMS.md`](CODEEXAM_PSEUDO_CLAIMS.md)'s HOF section,
[`claims-pipeline-state.md`](claims-pipeline-state.md) §4 and §9, and
[`litigated-claims-ground-truth.md`](litigated-claims-ground-truth.md); the issue was #310.

## 4. Real-world claim charts that cite code

**Why public filings.** Litigation records name an accused product, not a public codebase, so
there is no public answer key that says "this claim reads on this code". The nearest thing is a
party's own chart that cites a file or function of an open-source repository: advocacy, not an
answer key, but a real claim against real code, placed by someone with a stake. Such charts exist
because some litigation now targets open-source projects used by deep-pocketed defendants.

**Where the citations live.** In exhibits to complaints (claim charts, usually two columns),
in infringement contentions and motions about them, in expert declarations, and in complaints
that paste code into their narrative. A citation can be a line link, a file link with a function
named beside it, a file link, a document in a repository, a directory, a bare repository, or no
link at all with code quoted by name (`secp256k1_ecdsa_sign_inner()`, `main_impl.h`). Some
filings paste the code itself, as text or as a screenshot; pasted text is readable, a screenshot
carries nothing the search can read.

**The search.** `scripts/recap-claim-chart-search.mjs` runs fixed query shapes against
CourtListener's RECAP archive, which answers full-text queries over filed documents with no
account and serves the documents free; it downloads every hit, extracts the text, records every
repository citation with its granularity, and in a second pass reads code quoted by name with no
link. Sized 2026-10-20: "claim chart" with a GitHub link, 89 hits; a file-level GitHub link in a
patent-infringement filing, 188; "infringement contentions" with a file-level link, 23; "source
code" with "claim chart" and GitHub, 49; a motion to strike contentions with GitHub, 104; a
declaration with a file-level link, 164. The full run over six shapes read every hit: 161
dockets, 274 documents, 1.6 GB of PDFs, filed 2010 to 2026. Of the 274, 80 name at least one
function and 49 name three or more (33 of those with no file-level link); for 39 of the 49, the
limitation each row quotes is the patent's own claim text, fetched from Google Patents and
aligned to the row by its words (2026-10-21).

A further sweep for charts that cite source code without GitHub (131 documents) found 12 that
name code and 6 with three or more functions:
Interactive Games v. FanDuel (Android API names), Dolby v. Snap (x264 and x265 by name), Cellspin
v. Autel (a decompiled app). The catalog, the PDFs and the per-document text stay outside the
repository; [`real-world-claim-charts.md`](real-world-claim-charts.md) carries the generated
listing and the regeneration command.

## 5. The tests on those filings

**The catalog's placement.** For each document the catalog places every code name in the chart
row or complaint paragraph that cites it, and takes the row's limitation from the patent's own
claim text where the alignment is clean: on the 2026-10-20 run, 54 rows carry patent claim text
aligned at a median agreement of 1.00, 7 carry a whole claim, 23 are left as the chart quoted
them (14 declined as garbled, 9 with no matching claim).

**The agreement test** (`scripts/recap-chart-agreement.mjs`, page
[`claim-chart-agreement.md`](claim-chart-agreement.md)). For each filing: clone the cited
repository at the filing's commit, or the default branch on the filing date; index the whole
tree; fetch the asserted claims; then score CodeExam's choices against the litigant's reachable
names in both directions, found-of-cited and cited-of-chosen. Four tiers: reachability (are the
cited names in the index at all), a name rule with no model, `--claim-locate` blind (hiding the
codebase's identity from the model) and plain, and `--claim-chart` per element.

calls at $0.60 and three `--claim-chart` runs at $1.91.

  (`secp256k1_sha256_write`, `nonce_function_rfc6979`).
- **Worst, Core Scientific 1-10** (US 8,532,286, Montgomery reduction, secp256k1). The chart
  reads (b),
  "computing a modified operand using a reduction value, instead of a modulus used in performing
  a standard Montgomery reduction, to perform a replacement of a least significant word of the
  operand", onto `secp256k1_scalar_set_int`, and (c), "outputting the modified operand", onto
  `secp256k1_scalar_mul_512`, `secp256k1_scalar_reduce_512` and `secp256k1_u128_accum_mul`.
  CodeExam chose seven targets, all loaders and parsers (`secp256k1_ecdsa_signature_load`,
  `secp256k1_pubkey_load`, `secp256k1_keypair_load`, `secp256k1_ge_from_bytes`,
  `secp256k1_fe_is_zero`, `secp256k1_declassify`): none of six names, and the word `reduction`
  matched no symbol at all. PROGME and True Return also scored zero, but their keys are a
  complaint's pasted servlet code and a differences layer with no vocabulary in common with the
  claim; Core Scientific 1-10 is the worst because the chart's association is at least arguable and
  CodeExam's list has nothing to do with it.

**Reading the misses.** Judged by reading the code behind the litigant's rows and CodeExam's
own logs: five of the fourteen keys are not ones a claim-to-code search should be expected to
reproduce; two misses are enumeration depth, the function CodeExam found holds the lines the
chart cites; and the real misses trace to four mechanisms in CodeExam:

- *Raw-substring word matching* (bridged 2026-10-22, below): the symbol search matched a
  predicted word as a raw substring of the name, so `reduction` could not find
  `secp256k1_scalar_reduce_512` (zero candidates for the element, on a chart whose association
  is at least arguable).
- *One-hop navigation* (second hop added 2026-10-22, below): navigation was one hop from
  model-proposed symbols only, so `CKey::Check` and `secp256k1_ec_seckey_verify`, the
  accept-if-below-the-order test the MARA claim turns on, sat one call below the `MakeNewKey`
  that CodeExam reached and were never offered, on a chart whose association is exact.
- *A test filter keyed on directory names* (widened 2026-10-22, below): the test filter keyed
  on a `test/` directory or a `Test` token, so a project that kept `tests.c` and `testutil.h`
  beside its sources had its tests chosen as implementers.
- *A 25-per-element pool at scale* (reported, widened and tie-broken 2026-10-22, below): a pool
  of 25 candidates per element over a 93,776-symbol index with 871 `merge` and 989 `join`
  symbols is a sample, so a chart's sort-merge join may never be offered.

## 6. The realistic goal

A chart of a real claim against a confidential codebase, produced on an air-gapped machine with
a local model on a 16 GB GPU laptop, that a source-code examiner can defend in the terms of
[`CODEEXAM_PATENT_CLAIMS.md`](CODEEXAM_PATENT_CLAIMS.md)'s methodology section. Defensible means:
granular line or function evidence per row (citing a filename can provide a good lead, but is
generally not sufficiently granular); the target set stated, so an `ABSENT` row is read as
"absent from these targets"; reachability stated, which names were in the index at all;
verdict provenance, the engine, the build, the targets checksum and the command; reproducibility
under `--reproducible`; and the reading kept visible, since every verdict is a candidate match
for a stated reading. The cloud-engine path exists for open-source and non-confidential code;
the air-gapped path is the differentiated one for code under a protective order.

Section 1's caution holds at the goal as much as today: the chart is a draft for the examiner's
own, the rows and the retrieval are CodeExam's and the verdicts are an AI model's, and a model's
citation can exist without saying what the cell claims. The aim is a draft close enough to what
contentions and expert reports contain that the examiner's work starts from it, never one used
as-is.

## 8. Getting to the goal

In order, each step measured on the fourteen by the agreement harness before the next:

1. The four retrieval fixes from section 5, the two small ones first (stemming in the symbol
   search, bridged 2026-10-22; the test filter, widened 2026-10-22), then navigation depth with
   same-class resolution (the second hop, 2026-10-22), then the pool at scale (reported, widened
   and tie-broken, 2026-10-22); each re-measured on the retrieval fixture and the ledger as
   well, population-wide.
2. The targets-fed `--claim-chart` step in the harness, scored by the judge's labels, as the
   second tier.
3. The litigant-seeded drafter test (`recap-chart-drafter-ceiling`): pseudo-claims drafted
   from the functions a party cited, compared element by element to the asserted claim with a
   floor and a control, to learn whether the drafter can express the party's theory at all.
4. The next cohort: the substantive pairs of Table B, once their garbled text is re-extracted
   (Table B's note), then the two non-GitHub cases with hand-set public repositories.
5. Per-element retrieval everywhere (a), then local-model target generation (d), one pipeline
   (f, g), and the GUI (h); the self-test for any index along the way; the public sample set.

Also being considered as a step toward claim/code alignment is semantic searching; see
[#322](https://github.com/aschulman42-cell/code-exam/issues/322) for why this is not as easy a
step as might appear (e.g., it may require placing patent-claim text on the one hand and source
code on the other into the same embedding space).

## 9. Some clarifications

- **No verified claim-to-code answer key exists.** Litigation typically names revenue-generating
  products, not public codebases; the filings in Table A are advocacy, placed by a party with a
  stake, and a match with one is agreement with that party. Any individual litigant can be plain
  wrong (litigants are required to be reasonable, and allowed to be wrong).
- **A name match is a name match.** It is not a finding that the code meets the claim, and the
  litigant's names are the catalog's reading of a PDF.
- **One sample per row.** The cloud engine has no seed control; `--runs N` pools several.
- **The snapshot is the filing date, not the accused build.** The harness clones the repository
  at the commit the filing names, or the default branch on the filing date when it names none;
  the party may have read a release, a fork or a vendored copy, so a name absent from the
  snapshot may have existed in the build the party read, and the reverse.
- **Original assignee is not the asserting party** for roughly 165 of the first 385 litigated
  patents; who drafted a claim, and who sues on it, are often distinct.
- **The corpus is a sample**, selected by litigation exposure, skewed toward older,
  mass-asserted patents.
- **Model runs are not reproducible across days** at exploratory temperatures; use
  `--reproducible` for a pinned run.
- **None of this is legal analysis.** CodeExam does not construe claims.

## 10. Other AI tools that draft claim charts

General-purpose assistants draft claim charts on request. Asked for a chart of a claim against a
named open-source project, ChatGPT, Claude or Gemini will produce one with or without the code in
front of them, because the project may be in their training data (which is the motivation for
the `--blind` option). The project author's older notes on that, on Perplexity's patents beta,
and on GreyB's GPS claim-chart generator (a claim against prior-art patents or an uploaded PDF,
run there on two prior-art pairs) are towards the end of the
[softwarelitigationconsulting.com page on AI & patent claims](https://www.softwarelitigationconsulting.com/patclaim-ai-forthcoming-ai-related-ai-based-work-with-patent-claims),
and at other softwarelitigationconsulting.com sources cited therein.

A search on 2026-10-21 found the following cloud claim-chart services for licensing and
litigation teams, each described by its vendor and none verified here:

- &AI (evidence-of-use and invalidity charts, each citation reviewed before export),
- Patlytics (infringement, invalidity and charting, with evidence crawled from public sources),
- XLSCOUT's ClaimChart LLM (a patent number and target products in, a chart out),
- Solve Intelligence and
- Patdel Analytics.

Every one appears to chart against documents, manuals, specifications and web pages; none
describes reading source code, and none describes running off-line (air-gapped).

Differences from CodeExam's approach include:

- **Recall or discovery.** An assistant that has read a public codebase can reproduce a chart
  from memory, and nothing in its output says which. CodeExam's `--blind` hides the codebase's
  identity and paths, and the agreement test's blind and plain runs differ by one name at three
  filings, so a hit is discovery; on confidential code, memory is unavailable in any case.
- **Citations that exist.** A model writing a chart freely can cite a function that does not
  exist, or lines that say something else. CodeExam's deterministic code owns retrieval and
  verifies every name against the index; the model judges only code it was shown, and the
  provenance header records what it was shown.
- **Confidentiality.** A chart of code under a protective order generally cannot go to a cloud
  service; see [`SOURCE_CODE_PROTECTIVE_ORDERS.md`](SOURCE_CODE_PROTECTIVE_ORDERS.md) on "fully
  containerized" environments. CodeExam's air-gapped path runs the same commands on a local
  model, at the cost section 7 states.
- **Speed and polish** are where the products lead: a chart in minutes, exported to Word, with
  evidence from documents CodeExam does not cite at all today (see issue #305).
