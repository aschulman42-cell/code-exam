# The drafter's ceiling on real claims

*Status as of 2026-10-24. Every number on this page carries the date it was measured and the
number of runs behind it. The table is regenerated by
`scripts/recap-chart-drafter-ceiling.mjs --render`; the prose is revised by hand.*

*Terms, tied to the command line.* On this page **the grouper** is `--pseudo-claims --candidates
<file>`, the deterministic step that writes candidate groups of functions as an anchors list, no
model; **the ranker** is `--rank` added to that command, one comparative model pass that tags each
group `[P0]` to `[P3]`; **the drafter** is pseudo-claim generation itself, `--pseudo-claims
@<anchors> --claim-schema --claim-class both --claims-only`, the model call that writes a method
claim and a system claim from a group of functions; **the seed** is the anchors list the drafter is
given; **the judge** is this page's own comparison of a drafted claim with an asserted one, a model
call made by `scripts/recap-chart-drafter-ceiling.mjs` (its `compare` step), not a CodeExam
command; **the locator** is `--claim-locate`.

## The question

Given the very functions one party says practice the claim, does CodeExam's pseudo-claim
drafter write a claim that reads like the asserted one? The agreement harness
([`claim-chart-agreement.md`](claim-chart-agreement.md)) measures whether `--claim-locate`
finds the code a litigant cited; this page measures the other half of the distance. If the
drafter, seeded with MARA's cited functions and nothing else, does not write the order-q test,
then the drafter is the limit and the locator cannot be blamed for not finding it. If it does,
the distance between the patent's language and the code's mechanism is one the locator has to
cross on its own.

Said plainly, as the rest of the claim-chart pages say it: this is agreement with a party's
theory, not correctness. Any litigant can be wrong, so a drafter that writes the asserted claim
from the litigant's code has reproduced that party's reading, not confirmed it.

## The method

Per filing and repository, from the harness's work directory:

1. **Anchors.** The litigant's cited functions that the index holds, resolved to `file@symbol`
   (exact name first, then the last segment; where several files define the name, the chart's
   cited files first, then at most three per name), in chart order, capped at 24. Nothing from
   the patent reaches the drafter: no claim text, number, class or topic.
2. **Draft.** `--pseudo-claims @anchors.lst --claim-schema --claim-class both --claims-only`,
   so the seed yields a method claim and a system claim with their sidecar. A **floor** draft from
   a group of the same size taken from the grouper's own candidates
   (`--pseudo-claims --candidates`), the first group sharing no function with the litigant's set.
3. **Compare.** One model call per pair, element by element: the asserted claim's elements are
   Google Patents' divisions, classed as preamble, mechanism or generic; the judge returns MET,
   PARTIAL or ABSENT per element with the pseudo-claim's phrase quoted, and the pseudo-claim's
   elements with no counterpart. Three pairs per filing: the litigant-seeded claim against the
   asserted claim (**the measure**), the floor-seeded claim against the asserted claim (**the
   floor**), and the litigant-seeded claim against another filing's claim of the same art (**the
   control**).
4. **Score.** Mechanism elements met or partial over mechanism elements is the headline, with
   a strict count (MET alone) beside it; all elements and the reverse count follow. A measure is
   reported as a finding only where it exceeds both the floor and the control for that filing, on
   each read separately; otherwise the row says indistinguishable, which is itself the finding: a
   claim so generic any mechanism meets it, or a comparison the judge cannot make. The strict
   read exists because the first run showed PARTIAL to be lenient: the judge gave four PARTIALs
   to another signing claim of the same art on shared words such as "modular reduction".

## Reading the rows

The first three (2026-10-23, Claude Sonnet 4.6 as drafter and judge, one sample per row), read
as the questions the page opened with:

**MARA 1-11 (US 7,372,961 against Bitcoin Core): does the drafter write the order-q test?** It
writes the loop and the check as the code states them, not as the claim does. Seeded with the
eight functions the chart cites (`CKey::MakeNewKey`, `CKey::Check`, `secp256k1_ec_seckey_verify`,
`GetStrongRandBytes`, `MakeKeyData` among them), the method claim reads: "verifying the private
key candidate by loading the candidate bytes as a scalar on the secp256k1 elliptic curve and
confirming the scalar is within the valid range; repeating the generating and verifying steps
until the private key candidate passes verification". The judge marks the repeat MET and the
determination, acceptance and rejection PARTIAL ("checks validity but does not state this is a
less-than-q comparison performed prior to any mod-q reduction"). The hash step is PARTIAL for a
different reason: the draft's hash is the RNG's internal SHA-512 accumulator, and "B does not
perform a distinct hash H() on a seed value SV to produce H(SV)". The floor draft (an unrelated
Bitcoin Core group) meets nothing; the control (the same draft against ViaBTC's claim) meets
nothing. A finding on both reads, 6 of 6 mechanism elements met or partial, 1 MET. Read with the
chart of 2026-10-22, which found the same code's hash step absent and its range check assumed
behind an opaque callee: the distance on MARA's hash element is in the code, not in the locator
and not in the drafter. The drafter's ceiling here is the mechanism in the code's terms; the
claim's H(SV) is the claim's.

**Foundry 1-11 (US 8,806,197 against secp256k1): does the drafter write the recovery indicator?**
Yes: "computing a recovery identifier from the parity of the y-coordinate of the ephemeral point
and an overflow flag", MET, from `secp256k1_ecdsa_sig_sign` and the fourteen functions beside it.
The signature-component element is PARTIAL (the draft's r and s against the claim's first and
second components with an ephemeral public-key coordinate). The floor meets nothing. The control,
the same draft against Foundry 1-14's finite-field claim, is PARTIAL on four of six elements on
shared words ("modular reduction", "ephemeral point"), which is why the headline reads
indistinguishable from the control while the strict read, MET alone, is a finding (1 against 0).
That control row is the page's own evidence that PARTIAL is lenient and that the strict column
belongs beside the headline.

**Securitize 15-9 (US 12,099,996 against dstoken): does the drafter write the remote signing?**
No, and the row's numbers understate how clearly. The asserted claim is 25 elements, a system
claim whose processor, memory and interface boilerplate the classifier calls generic, along
with most of the signing and verification sub-elements, so the headline counts five mechanism
elements and reads 2 of 5 met or partial (the whitelist restriction and a verification
sub-element, both PARTIAL) against a floor of 1 of 5 and a control of 1 of 6; a finding on the
headline, indistinguishable from the floor on the strict read, with no MET anywhere. Read the
elements, not the counts: every element that involves the remotely located device
cryptographically signing data, communicating it, and the system verifying that the target
address derives from the private key that signed (A3, A10, A12, A14 to A18, A21, A24) is ABSENT.
The draft, seeded with `transfer`, `transferFrom`, `recordTransfer` and six more, writes
compliance gates, a token ledger and investor-count recording, which is what those functions
do. The cited code does no signing; the claim's signer is another machine. The chart judge of
2026-10-22 read the same claim's signing onto the permit path; the drafter, given only the
litigant's functions, does not reach it at all. Agreement with the litigant's citation, here,
would have been the error.

**Across the three.** The drafter reaches what the cited code does and writes it in the code's
terms; it does not write what the claim asserts beyond the code (MARA's H(SV), Securitize's
remote signer), and a judge that counts PARTIAL will credit shared vocabulary across claims of
one art. The reverse lists (B-only: 13, 9, 8 elements) are the code's specifics the claims do not
recite: nonce iteration and blinded multiplication for Foundry, secure-memory handling for MARA,
investor-count recording for Securitize.

**Across the fourteen** (the table above, 2026-10-23, the same engine, one sample per row).
Fifteen pairs scored; VM Innovations' circlefin and go-ethereum repositories have no anchor the
index resolves (the chart's cited names there are a local's `wait` four ways) and stay unscored.
On the headline read, eleven of fifteen measures exceed both their floor and their control. On the
strict read, three: ViaBTC (2 MET of 2), MARA and Foundry 1-11 (1 each); on the other twelve the
judge never says MET, only PARTIAL, which is the granularity gap of the page's question stated
as a number: given the litigant's own functions, the drafter writes the mechanism at the code's
grain, and the claim's element is met in part. Two measures are zero from the litigant's own
anchors, Databricks (0 of 3) and PROGME (0 of 4), the two whose anchor lists were capped at 24
(from 44 and 30) in chart order, so the cut may have taken the crux; a re-run with the cap lifted
is the obvious next measurement. One floor beats its measure, Core Scientific 1-8 (floor 4 of 5
against 3 of 5): a claim an unrelated secp256k1 group meets as well as the cited one, which is
what the floor exists to say. True Return has no floor: dss's 262 symbols yield no candidate
group disjoint from the cited set, so its row is read against the control alone. Every
comparison parsed on the first call. Cost: 29 drafts at $2.81 and 52 comparisons at $0.53, $3.34
for the fourteen. The floor's deterministic grouper (`--pseudo-claims --candidates`) took 52 minutes on
Spark's 93,776 symbols and 91 on xbmc's 57,568, a cost of its own worth an issue.

## The other half: CodeExam's own groups as the seed

The table above seeds the drafter with what a litigant cited. The question Andrew put on
2026-10-24 is the reverse: seeded with what CodeExam finds on its own, does the drafter write the
asserted claim? That is the "synthetic data" use of pseudo-claims as a test bed for claim charts,
with the public filings as the answer key, which is agreement with a party, never correctness.

Per filing and repository, the `ce-seeded` step of the same script:

1. **Rank.** `--pseudo-claims --candidates <file> --rank`: the grouper's candidate groups with the
   ranker's priority tag (`[P0]` to `[P3]`) in each header, highest first, under CodeExam's own
   cost guard. A repository the guard refuses is recorded as not run, with the projection.
2. **Select.** The top three groups by priority, ties in list order, groups under three functions
   skipped, each group's anchors capped at 24 as the litigant's are. The group's **overlap** with
   the litigant's cited functions is recorded by symbol name: a group that holds the cited
   functions is the litigant-seeded measure under another name, and zero is the expectation.
3. **Draft and compare.** The same drafter call and the same judge call as above: the group's
   claim against the asserted claim (**the measure**) and against the paired filing's claim of the
   same art (**the control**). No floor of its own: the group is a CodeExam group. The row sets
   the litigant-seeded measure and floor of the same pair beside it.

### What the two halves say

The question both tables serve (Andrew, 2026-10-21 and 2026-10-24): given the code references in
a litigant's claim chart, how close does CodeExam's pseudo-claim, drafted from those references,
come to the asserted claim, and how much of that closeness is the references' doing. The first
table answers with the references, the second without them, each row judged the same way against
the same claim.

**With the references** (2026-10-23, 15 of 17 pairs scored): the pseudo-claim reaches met or
partial on the claim's mechanism elements, above a floor group and a control claim, on 11 of 15
pairs; it reaches MET, the same limitation in substance, on 3 (ViaBTC 2 of 2, MARA 1 of 6,
Foundry 1-11 1 of 2). Everywhere else the elements are PARTIAL: the drafter writes the mechanism
at the code's grain and the claim states it at the patent's. What a claim asserts beyond the code
is not written from any seed.

**Without them** (2026-10-24, 14 pairs, CodeExam's top three groups each, 42 rows): 12 rows above
their control on the headline read, 2 on the strict read; against the litigant seed of the same
pair, best of three, 2 pairs closer (FriendliAI, Core Scientific 1-8), 6 as close, 4 at zero where
the references had scored (Foundry 1-11, MARA, ViaBTC, consensus-specs). The four are the claims
whose crux is one mechanism in one place, and in each the cited code sits low in CodeExam's
ranking, "standard-pattern", "crypto plumbing" or "third-party". On the arithmetic claims
(Foundry 1-14, the Core Scientific pair) any field or scalar group writes the claim, which the
controls confirm. Five picks were yesterday's floor groups re-drafted; four moved by one element.

Four rows, with the asserted element beside what the drafter wrote:

- **Close, with the references. ViaBTC 1-6 (US 8,788,827) against Bitcoin Core**, 23 cited
  functions. Asserted: "generating, by operation of a cryptographic module comprising one or more
  processors, a public key of the signer based on the elliptic curve point and a hash value e
  computed from the message M". Drafted: "deriving scalar multipliers u1 and u2 ... performing an
  elliptic-curve multi-scalar multiplication ... to obtain a recovered public key point". MET;
  both mechanism elements MET, the recovery written as the code does it.
- **Close, without them. VM Innovations 1-23 (US 12,093,999) against the coinbase SDK**, the
  ranker's first pick, the staking group, no cited function in it. Asserted: "signing each of the
  unsigned blockchain transactions with a corresponding custodial private key". Drafted: "apply
  the cryptographic signing key to produce a signed payload". MET, with the batch broadcast and
  the completion poll PARTIAL ("submit a broadcast-staking-operation API call", "reload the
  staking operation object at a configurable interval until ... a terminal state"): 5 of 10, as

- **Distant, with the references. Securitize 15-9 (US 12,099,996) against dstoken**, 9 cited

  sign data by cryptographically transforming the data using a private key". Drafted: "A system

**Confirmation or not.** For pseudo-claims as a description of code: a confirmation, within
limits. Given the code a claim reads on, the drafter writes that code's mechanism in claim form,
faithfully enough that a comparison finds the asserted elements in it in part on 11 of 15 pairs
and in full on a few, and it does not write what the code does not do (Securitize). For
claim-to-code matching unaided, the harder half of CodeExam's claim-chart work: not a
confirmation. Where a claim turns on one specific mechanism, CodeExam's own ranking of the
codebase does not surface it in the top three, and the drafted claims from what it does surface
share nothing with the asserted one; where the ranking's picks match the claim, the claim is one
most groups of the codebase would match. The limit this test exposes is in the ranking, which
orders by where to look first in an unfamiliar codebase, not by what a patent recites; the
drafter writes what it is given. It is the same limit the agreement harness measures from the
other side, where `--claim-locate` reaches 24 to 28 of the 153 cited functions (2026-10-22).

**Does `--rank` improve what `--pseudo-claims` brings to the surface as litigable?** (Andrew's
question, 2026-10-24.) This test cannot say whether `--rank` improves on no ranking: it drafted
the three top-ranked groups per repository and never the unranked top three, so there is no
comparison arm. What it can say is where `--rank` points. `--rank` surfaces what it was built to
surface: its rubric orders the grouper's candidate groups by where to look first in an unfamiliar
codebase, codebase-specific mechanisms at P3, standard patterns and library wrappers below,
vendored third-party code and generated code last. On these fourteen filings it did that, putting
secp256k1's distinctive arithmetic and Bitcoin Core's coin selection and transaction graph at P3,
and the claims the litigants asserted read on code the same rubric demotes: ECDSA signing as a
"well-known protocol flow" (P1), key generation as "crypto plumbing" (P2), every function ViaBTC
cited inside Bitcoin Core's vendored secp256k1 as "third-party" (P2). "Litigable" is a different
ordering from "look here first": asserted patents often read on standard mechanisms, and a
vendored library is still the defendant's shipped code. `--rank`'s notion of priority points away
from where these fourteen patents land, with two exceptions where the claim targets a codebase's
own distinctive mechanism (FriendliAI's batching, the coinbase SDK's staking) and the first-ranked
group matched or beat the citation. One default compounds it: with a ranked list, `--min-rank`
defaults to P2, so `--pseudo-claims @<ranked list>` with defaults drafts nothing tagged P0 or P1,
among them the three ECDSA groups that hold `secp256k1_ecdsa_sig_sign`.

**Could a ranking be built for this scenario?** The ordering wanted is an odd one: not "what is
distinctive here" but "what would a hostile party find significant here", a prediction about
other people's patents. The fourteen suggest some of its features, a sketch and not a plan:
in-house implementations of commonly asserted mechanisms (signing, key generation, batching,
transfer compliance) ranked up rather than down; vendored code kept in the running when the
question is exposure rather than authorship; the grouper's groups scored against the vocabulary
of asserted-claim preambles, which the agreement harness already holds for the fourteen and which
Google Patents could supply at scale; and, where a user has a patent or an art area in mind,
`--claim-locate` is already the claim-aware path and needs no ranking. Whether any of this would
beat `--rank` is untested, and fourteen filings are probably too small a sample to design from.
The right next step is a comparison arm on the same pairs, unranked, `--rank`, and a sketch like
this one, before anything is built.

**Limits of the test.** One model, Claude Sonnet 4.6, as ranker, drafter and judge; one sample
per row, with a spread of about one element; PARTIAL is lenient, so the strict column is the
conservative read; fourteen filings, three pairs not run on the second half; the asserted claims
are a party's contentions, so every match is agreement with that party, not correctness; the
second half drafts the top three groups only, and the cited code was in every list, lower down;
groups over 24 functions are cut in the grouper's order. Cost of the second half $11.42, wall
clock 2 h 8 min, most of it the grouper on the four large indexes.

## Caveats

- Agreement with a party, not correctness.
- The drafter cannot run blind: it reads the code and its paths.
- One sample per row unless `--runs N` says otherwise; the spread is reported where it was run.
- Anchors are capped at 24; Databricks's and PROGME's long lists are cut and the rows say so. A
  ranked group over 24 is cut to its first 24 in the grouper's order, which on secp256k1's scalar
  group put eight benchmark functions in the seed; 12 of the 42 ce-seeded rows are capped.
- Claim 1 and its dependents only.
- The comparison judge is a model; the floor and the control are its calibration, and a judge
  that cannot tell the measure from either has said so in the row.
